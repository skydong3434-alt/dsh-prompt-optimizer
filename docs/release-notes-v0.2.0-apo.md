# v0.2.0-apo — Adaptive Prompt Editor

> GitHub Release Notes（草稿，发布时直接使用）。
> 上一版：`v0.1.0-apo`（仍指向 `c88e922`，未移动）。

## What changed

- **不再需要选择任务类型**。主界面移除了 AUTO / Research / Planning / Execution 等类型下拉；
  自动判断成为默认行为。
- **自动判断四件事**：任务意图、Prompt 类型、目标模型、需要修改多少。
- **四档改动幅度**：**无需修改**（原文逐字保留，不调用模型改写）、**局部修补**（只补少量缺口，
  不重排、不加章节）、**重新整理**（去重重排，不新增你没提过的目标）、**重新构建**
  （先问清关键取舍再从零构建，只写完成任务真正需要的信息）。
- **Requirement Discovery**：真正需要你拍板、且会显著改变方案的信息（范围取舍、
  一次性验证 vs 长期自动化、只分析 vs 真执行、能否修改/删除、不可逆动作授权…）
  会先问少量关键问题（单轮 1–3 条），**在你说清楚之前不生成提示词**。
- **Requirement Ledger**：你说过的决定被记为台账；之后改措辞重新优化时，
  仍然成立的要求**会被保留**，不重复询问。
- **Agent 可自行调查的信息不再变成 `[待补充:]`**：版本、路径、接口地址、项目结构、
  依赖、现有实现这类可读事实，改成「交给执行方动手前确认」的动作式指令或分支条件。
  **旧的 `[待补充:]` 占位符机制已退出正常生产路径。**
- **Image / Video 专用描述式 contract**：生图 / 视频提示词按视觉要素组织，不再套用
  「目标 / 阶段 / 任务 / 测试」这类项目任务模板。
- **Validator 可控回流**：交付前校验带稳定原因码、有次数上限、不会无限循环；
  伪造来源、丢失你已确认的约束、空交付稿都不会被静默交付。
- **re-optimize 需求对账**：旧台账按「仍然成立 / 与新内容冲突 / 已不再适用」三类裁决。
- **结果页只给本次判断摘要**（如「重新构建 · Agent 执行任务 · DSH」），
  展开「查看分析」才显示内部细节（含 `REBUILD` 这类内部枚举）。

## Why it matters

旧版是**固定模板式扩写器**：它倾向于把任何输入都套进同一套模板，并把「读一下就知道」的
信息写成 `[待补充:]` 让你自己填。结果是：已经写得不错的 Prompt 被改写、简单需求被扩写成
项目计划、你能自己查的版本/路径也要你回答。

v0.2.0-apo 改为**自适应编辑器**：先判断该不该改、该改多少，再决定写成什么形态；
能自己查的不问你，真正要你拍板的才问你，问过的记住不重复问。
同语料真实对比（25 条，同模型）：交付稿中的 `[待补充:]` 从 **635 次 → 0 次**，
KEEP 从「改写 + 占位符」变为**逐字保留**。

## How to use

1. 在输入框写下你的 Prompt（口语化也行）
2. 点「优化」

就这样。**通常不需要选择任务类型。**

- 如果出现少量关键问题：先回答（或选「按你的判断继续」，它会按安全默认推进并把该决定标为暂定）。
- 结果面板：摘要 → 「查看分析」（可折叠）→ 已确认需求 / Agent 自行调查 / 暂不影响 → 优化稿。
- 满意就「替换输入框」，然后**由你自己发送**（插件从不自动发送）。

典型支持：Research · Planning · Execution / Coding · Diagnostic · Review · Creative ·
Image Generation · Video Generation（文生 / 图生 / 首尾帧）。

## Upgrade notes

- **从 `v0.1.0-apo` 升级无破坏性变更**：安装方式、设置项、按钮位置与「不自动发送」承诺不变。
- **行为变化（有意为之）**：主界面的类型下拉不再显示；`[待补充:]` 不再出现在交付稿中；
  已完整的 Prompt 会**逐字保留**而不是被改写。
- 若你过去依赖下拉手动指定类型：改用结果页折叠区里的**「调整判断」**（低优先级高级入口）。
  注意优先级为「正文明确约束 > 手动指定 > 自动判断 > 优化器建议」——
  例如正文写了「只检查，不修改文件」，即使手动选了执行，也不会突破这个约束。
- 旧 tag `v0.1.0-apo`（`c88e922`）保留不动，可随时回退。

## Known limitations

- **推理型模型在分析阶段需要较大的输出预算**：预算不足时分析会降级为兜底判断，
  此时流程仍安全（机械安全层保证关键决策不被跳过），但意图/目标判断的精度会下降。
- **Requirement Discovery 的具体问题措辞可能因模型而变化**，但**关键决策由机械安全层保护**：
  同一句模糊输入不会出现「有时问你、有时不问」。
- **高级「调整判断」入口仍然存在**，但正常用户通常不需要使用。
- **Image / Video 的要素取舍仍由模型判断**：不同模型可能给不同详略程度；本版不做
  「所有模型完美适配」的承诺。
- 后续 tuning 将基于**真实失败样本**，而不是继续扩大当前版本架构。
