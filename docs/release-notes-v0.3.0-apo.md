# v0.3.0-apo — V3 单次调用自适应优化器

> 发布标识:`v0.3.0-apo`(2026-10-10)。上一版 `v0.1.0-apo`。
> `v0.2.0-apo`(v2「自适应提示词编辑器」)**从未打 tag、从未发布**,其多阶段架构已被本版本
> 整体替换,仅作为历史记录保留在 CHANGELOG 中。
> `package.json` 的名义版本沿用上游 `0.4.0`(派生包名不变,见 NOTICE §3)。

## 这一版做了什么

把优化器从「多阶段自适应编辑器」收敛为**单次调用**的自适应优化器:

- **一次模型调用完成优化**。普通请求不再「先分析、再编译」,直接产出优化后的提示词。
  实测同一条输入的端到端耗时从约 134 秒降到数秒级(平均约 5 秒),模型调用次数 2–4 次 → 1 次。
- **只在真有必要时问一个问题**。只有原文存在**语义歧义**(指代不明,且上下文里也找不到对象)
  才提一个关键问题,回答后立即继续;不再重复确认。实现细节类信息(路径、接口、版本、技术选型、
  workflow、测试命令)一律不提问。
- **不再擅自扩展任务方向**。目标描述不会被改写成规划任务,想法交流不会被改写成执行任务,
  模型给出的建议不会被写成你的明确要求。输入已经清楚时按保守方式优化,简单输入保持简洁。
- **特殊用途只按明确证据触发**。只有明确要「生图 / 视频 / 音频提示词」或「写给某个执行 Agent」
  才套用对应形态;仅出现关键词不改变用途,且这些形态不会被写成执行任务模板。

## 为什么重要

v2 的链路是「分析 → 分诊 → 需求发现 → 台账 → 编译 → 校验 → 策略路由」。它很完备,但代价是:
一次普通优化要跑 2–4 次模型调用,还会为了「补齐需求规格」反问一串执行期信息;
用户只是想把自己的话理顺一点,却拿到一份项目规格书。

V3 的判断是:**优化器的第一职责是忠实理解并表达你想做什么**,而不是替你补完一份需求文档。
所以需求发现、台账、二次校验、策略路由这些机制被整体删除(约 13.7k 行),
`src/core/` 只剩 `v3.ts` / `triage.ts` / `types.ts`。

## 怎么用

1. 在 DSH Desktop 的输入区写下你的请求(目标、想法、待优化的提示词、代码任务都可以)。
2. 点「✨ 优化」。
3. 普通请求直接出结果;只有真正的语义歧义才会先问你一个问题,答完立刻继续。
4. 结果面板给出优化后的提示词 + 一段中文说明(本次怎么判断、改了什么),然后替换 / 复制即可。

不需要先选任务类型。用途(GENERAL / IMAGE / VIDEO / AUDIO / AGENT,可叠加「严格 JSON」)
由输入内容判断。

## 保留的安全能力

- **硬性约束核对**:输入里的硬性约束(不要 / 不得 / 仅限 / 不允许…)会在交付前做一次**机械核对**
  (不额外调用模型)。改写成语义等价的说法不会误报;真的丢了约束仍然会报「约束核对未通过」。
- **意图扩展拦截**:模型把「一个目标」写成「一份实施方案」这类擅自改变任务方向的输出会被拦下,
  回退为保守优化。
- **技术错误如实显示**:模型没产出、超时、协议异常都显示为可重试的技术错误,不伪装成「需要你澄清」。

## 已知限制

- **模型波动仍然存在**。规则与机械核对能挡住方向性错误(丢约束、擅自改任务、模板漂移),
  但同一输入的措辞、详略、补充维度仍会随模型采样变化。本版本按真实失败逐条收紧,
  不宣称「永不误判」。
- **推理模型的时间预算**。推理型模型(思考写在 `content` 里、`reasoning_content` 为空)已做
  剥离处理;超长输入下仍可能出现较长的端到端耗时。
- **澄清的措辞由模型生成**。问什么由规则约束(只问语义歧义、一轮最多一个),具体句子不固定。
- **复杂研究 / 评估类请求的输出仍会比较长**。这是任务量级决定的,不是模板补齐。

## 升级说明

- 从 `v0.1.0-apo` 升级:直接更新即可。输入区不再有任务类型选择;结果面板不再显示
  任务类型 / 把握度 / 提示词目标 / 编辑分诊等旧字段。
- 从 `v0.2.0-apo` 的发布准备版本升级:该版本**从未发布**,不存在需要兼容的正式安装。
- 运行版本一致性提醒:DSH Desktop 的宿主模块**只在进程启动时加载一次**。
  更新代码并重新 build 之后,必须**完整重启 DSH Desktop** 才会生效;刷新页面只更换客户端 bundle。
